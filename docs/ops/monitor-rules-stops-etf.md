- **`python -m landry monitor status|stamp|refresh` (built 2026-10-05, `landry/monitor_tab.py`, Journal row 98) keeps Monitor & Recheck Triggers current for HELD positions -- Alan: "keep Monitoring tab monthly-current for held positions".** Two things on that tab go stale for different reasons. **Last Score (cols C-G)** is event-driven, not calendar-driven (Instructions A52; month- and quarter-end drive other things): it must mirror the held position's Scoring row -- Date Scored, composite, Tier 1 average, decision, and Price at Last Score = the last close on or before the date scored (the Friday close for a weekend date) -- and must be re-stamped after ANY re-score or Decision change, including a rule change that moves Decisions with no re-score (the 10/4 Rule 3 change did). Nothing in the code did it until now, so the 9/13 held-position re-score of 14 names and the 9/30 ADBE / PLD reconfirmation were never stamped (CRWD read 70.4 BUY, 8/6/26 against 63.4 AVOID; found 10/5); `stamp` fixes every held scored ticker that does not mirror Scoring (or the named ones), whole rows or nothing, and needs a recalculated workbook because Scoring's composite and decision are formulas. **Insider / analyst signals (cols K-N)** are "refreshed periodically, not live": SEC Form 4 over a 30-day lookback plus yfinance's 3-month consensus drift (`landry.data_auto`); `refresh` rewrites them for the held names (about 90 seconds) and dates the day in Q1 (defined name `MON_SignalsAsOf`) only when every ticker answered. yfinance sometimes has no 3-month-ago breakdown (VRTX, PLD, V, ANET, KLAC, TSM on 10/5): `analyst_shift_detail` calls that "no_history", the cell keeps its value and it does not hold the month open; a real error does. `landry audit` has `monitor_last_score` and `monitor_signals` (refresh within 35 days) and, being outside `STANDING_AUDIT`, both make the Saturday weekly run say NEEDS ATTENTION when they lapse -- that is the monthly nudge; the weekly run neither stamps nor refreshes (offered, not built). Run `monitor refresh` about monthly (the 7th-of-month DCA tranche prep is a natural slot) and `monitor stamp` right after a re-score.

- **`python -m landry rules-list [--check] [--pdf]` (built 2026-10-05, `landry/rules_list.py`, Alan: "create an updated Rules list for printing") writes `docs/Landry System Hard Rules List v<version>.docx` (+ PDF with `--pdf`): all 51 numbered Hard Rules of v1.05 by Part in condensed wording, plus a quick-reference page (decision bands, sizing, drawdown response, macro overlay, Hold Through, the Stop-Review Ladder, conflict order, what to avoid); six Letter pages, Calibri.** The rule numbers are one running sequence, so a hand-kept cheat sheet goes stale the moment a rule is inserted (see the numbering bullet below) -- so the wording lives in `PARTS` in `landry/rules_list.py` and `check()` reads the rulebook docx itself (the numbered paragraphs of its INDEX -- MASTER RULE REGISTER; Word's own auto-numbers) and fails on a different version, a different count or numbering of rules, or any number in a rule's wording that the rulebook's rule does not contain (it tests numbers, not prose: read a changed rule by eye). `tests/test_landry_rules_list.py` runs it against the live rulebook, and `rules-list` refuses to write a list that fails it (`--force` overrides). **After any rulebook revision:** the test fails -> update `PARTS` (wording, numbering) and `VERSION` / `REVISED`, run `rules-list --pdf`, re-print. **Found writing it (the Instructions tab's stale v1.03 header and rule reference were fixed 10/8/26 with v1.05; the same lines are embedded in the rulebook's Appendix and were updated there too):** `landry/*.py` docstrings and `tests/test_landry_rule_register.py` still cite the v1.02 numbering of 49 rules (tax is Rules 38-42 there and 40-44 now: old 5-32 moved up one, old 33 and later up two).

- **`python -m landry stops [--live]` and `stops record TICKER --conclusion reaffirmed|resized|referred ...` (built 2026-10-08, `landry/stops.py`; policy: Journal row 109, Alan: "controlled, rule-driven") is the stop-review ladder's check.** The rulebook has no price stop-loss and a 110-stock test (Journal row 108) says mechanical stops cost 3-14 points and whip-saw ~2.4:1, so a falling holding gets a deadline-bound re-underwrite instead of a sale: RUNG 1 = 20% below cost basis AND (Relative Strength vs SPY 1 OR price under its 200-day average) -> no additions (DCA included), a documented re-underwrite within 10 trading days (fresh Tier 1 reread incl. leading indicators like net new ARR / RPO, the Rule 5 review in the Journal), repeated every 90 days; RUNG 2 = 30% below cost + the re-underwrite found deterioration -> trim a third (a second confirmation another third); RUNG 3 = 40% below + RS 1 + 8 weeks under the average -> Exit Review. It only REPORTS: cost basis from Current Positions (all accounts), prices from Market Data, the 200-day average = the last 40 weekly closes in Price History, RS = 26-week return vs SPY with `--live` (one Yahoo request) else the recorded Scoring RS score. What it cannot know -- that a re-underwrite was done and what it found -- lives in `landry_stops.json` (tracked; ADBE reaffirmed 10/8, next check 12/9), written by `stops record` after the Journal entry. `landry audit` fails `stop_review_ladder` whenever a holding is on a rung without a current review (or a rung-2 trim / rung-3 exit is pending), and `landry weekly` prints a `Ladder` line, so Saturday's report says NEEDS ATTENTION until it is written. A review that froze additions keeps them frozen while it is current (90 days / its next check) even if the price wobbles back above -20%. Exit status 2 = needs attention.
