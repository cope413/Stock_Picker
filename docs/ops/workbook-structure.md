# Workbook structure, page setup, row surgery, Excel/LibreOffice traps

<!-- Moved verbatim from CLAUDE.md on 2026-10-09 (token diet). CLAUDE.md names the files to read before touching each area. -->

- A full-teardown-rebuild of a worksheet (`wb.remove()` + `wb.create_sheet()`, the standard pattern for any structural change) starts with **zero** page setup. Explicitly capture and restore `page_setup` (paperSize/scale/orientation), `page_margins`, and `oddFooter`/`oddHeader` (text+font+size per section) from the last git commit or another already-correct tab — not just font/fill/column-widths. This has been missed and had to be re-fixed more than once; neither recalc nor a value diff will ever catch it.

- Separately, `python -m landry.xlsx_recalc` itself round-trips the file through headless LibreOffice (`soffice`), and that resave normalizes page setup — an explicit `scale` (e.g. 100) tends to come back unset, and `paperSize` can shift to whatever LibreOffice's own default resolves to on this machine (observed: unset → 1/Letter). Found 2026-09-13 when a deliberately-set custom scale on Journal (83%, tight margins, for a print-friendly layout) got silently wiped by the very next mandatory recalc. Since recalc is required after *every* save, a custom non-100% scale on any sheet in the main workbook cannot currently survive — there's no way to both keep cached formula values correct (needs recalc) and keep a custom scale (recalc erases it) with the current tooling. If a sheet genuinely needs a non-default print layout, put it in a standalone extract file instead (see `LANDRY_SYSTEM_WORKBOOK_25_JOURNAL_COPY.xlsx` below) where there's no formula/recalc round-trip to fight. Fixing this properly would mean having `xlsx_recalc` snapshot and reapply page setup via the same LibreOffice pass (a UNO macro), not an openpyxl pass afterward (which would just wipe cached values again) — not done, not urgent while paperSize keeps landing on the correct value (Letter) anyway.

- When a rebuild shifts a tab's column or row positions, grep every *other* tab for `'<TabName>'!` references before calling it done — a within-sheet check never surfaces a stale cross-tab reference. `landry audit` catches most of this automatically now, but it doesn't catch every case (e.g. a formula that still resolves to a *valid but wrong* cell after a column shift — see the Recommended Action bug, or the DCA-CATCHUP-1..8 label collision, both found by hand).

- **Row surgery with openpyxl (`insert_rows` and friends) silently leaves behind everything that isn't cell text — merged ranges, row heights, and every formula whose references aren't inside a Table's structured refs — and Excel is the only thing that notices.** Found 2026-10-02, when Excel answered the workbook with "We found a problem with some content … recover?": the 9/30 GE/NFLX insertion on Current Positions left the note's merge (A50:M50) behind, now *inside* the grown `CurrentPositionsTable` (Excel cannot represent a merged cell inside a Table), and the note itself in an un-merged 11-wide wrapped cell that LibreOffice auto-fit to 941pt (Excel's maximum is 409.5pt). The same surgery wiped the COMBINED PORTFOLIO TOTAL row (a write into a merged range is silently dropped) and left the Excluding-Cash and Cash / Cash Equivalents formulas pointing at their old rows (cash read $396K instead of $469K, the cash % blank) — unnoticed for three days because nothing outside the block reads it. Repaired 10/2 from the pre-surgery workbook (git `f7bbe36`), the total verified against `total_portfolio_value` to the cent. Guards now: `landry audit` has `merges_inside_tables` and `row_height_ceiling`, and `xlsx_recalc` caps any row above 409.5pt on every save and returns `clamped_rows` — if that is ever non-empty the note needs a better layout (merge it across the table width), the cap only keeps the file openable. After ANY row insertion: unmerge/re-merge, re-set heights, re-derive every formula below the insertion *by ticker, not row arithmetic*, write merged-range cells only after unmerging, and open the result in real Excel once — LibreOffice and openpyxl accept files Excel rejects. **Since 2026-10-07 a position is added to Current Positions with `landry.cp_tab.insert_position(wb, account, ticker, description, asset_class, quantity, cost_basis, price)`, never `insert_rows`:** it moves everything below the block down one row the way Excel would (cells with styles, row heights, merges, the Table range), rewrites every same-sheet reference by `shift_formula` (a block-sum range ending on the row above grows to take the new row), copies the block's last row's formulas, and refuses (`CurrentPositionsError`) rather than guess when the sheet's structure differs; `fix_excluding_cash` re-derives the "Excluding Cash" line by ticker. `tests/test_landry_cp_tab.py` pins it, including the invariant that adding a zero-share row to the live workbook changes no number. It still needs the open-in-Excel check. First used for VEEV (row 24, Journal row 104); the same pass found the JT ULTRA "Excluding Cash" line had subtracted Visa's cost instead of FZFXX's since the 9/8 insertion (7.2% -> 6.3%). Known and deliberately left alone (Alan, 10/2): FZDXX/FZFXX cost basis wasn't reduced by the $44,541.75 spent on GE/NFLX, so Combined unrealized G/L reads ~$15K instead of ~$60K — an interim estimate that corrects itself on the next real Fidelity export; don't hand-fix it.

- **LibreOffice's recalc will NOT catch a circular reference that Excel reports -- and Excel is the only thing that does.** Found 2026-10-05, before it reached Excel, on Performance Tracking: `Shares` used `SUMIFS($T:$T,$A:$A,…,$I:$I,…)` with whole-column ranges, column I also holds the summary block's Excess formulas, and those depend on Shares -- a range-level cycle (`I47 -> G47 -> D47 -> V10 -> U10 -> I47`). Excel treats a formula as depending on EVERY cell of a range it reads, whether or not SUMIFS needs that cell, so it would have shown a circular-reference warning and zeros; LibreOffice evaluates SUMIFS lazily, calculated correct numbers and reported 0 errors. So: never read whole columns from a formula on a tab that also holds formulas below its table; bound ranges to the table's rows. `landry.perf_tab.find_cycles(wb)` does the range-level search for that tab (the audit's `performance_tracking_ties:cycles` runs it every time); if another tab gets formulas that read whole columns, run the same kind of check -- a clean recalc proves nothing about this.

- `ws.tables.items()` in this openpyxl version yields `(name, ref-string)`, not `(name, Table object)` — use `ws.tables[name]` (bracket access) to get the real Table object with `.ref`, `.tableColumns`, etc.

- **`ws.cell(row=r, column=c, value=None)` does NOT clear an existing cell.** The constructor only assigns when the value is truthy/not-`None`, so this call is a silent no-op on a cell that already has content — cost real time on 2026-09-13 debugging why a "clear this row" script kept appearing to do nothing. Clear a cell with explicit attribute assignment instead: `cell = ws.cell(row=r, column=c); cell.value = None`.

- **A tab that formula-mirrors another (Dashboard mirrors Scoring row-for-row) needs its own row range extended every time the source tab grows a row** — this is a *fourth* variant of the cross-tab-drift problem, distinct from a stale column reference or a truncated range formula, because each mirror row is a single-cell reference (`=IF(Scoring!A48="","",Scoring!A48)`) that `landry audit`'s `check_cross_tab_references` doesn't flag (it checks header validity and range coverage, not "a whole row is simply missing"). Found 2026-09-13: Dashboard's mirror stopped at Scoring row 47, so KGS (added 9/11, row 48) was already invisible on Dashboard before ABT/SLB made it worse. If you add a new ticker row to Scoring, check whether Dashboard's last mirror row still covers it — `landry audit`'s `table_ref` check *will* catch the resulting Table-ref-vs-data mismatch once you extend the mirror rows but forget to extend `DashboardTable`'s own ref, and `schema_ref` will catch Schema Reference's row-range note going stale after that — but nothing catches the missing mirror rows themselves.

- **Scoring's Composite Score gate (col AF) now requires every Tier 1/2/3 indicator individually populated**, not just "the tier's contribution cell happens to be non-blank" — fixed 2026-09-13 tab-wide when GE became the first ticker ever scored with a genuinely partial Tier 2 (3 of 4 quant indicators drafted, Management Quality still pending a human call). The old gate would have silently computed Composite treating the missing indicator as a 0 contribution instead of waiting. Same idea as the Tier 1 Wtd Avg zero-padding fix from the KGS addition — if you're populating Tier 2/3 for a new ticker, do all of a tier's indicators in one pass rather than leaving it partially filled between saves, even though the gate itself is now safe either way.

- **Never sort or re-order the Scoring tab (or Dashboard), in Excel or in code -- filter instead (found 2026-10-08).** Dashboard and Entry Checklist mirror Scoring row for row by formula (`=IF(Scoring!A49="","",Scoring!A49)`), and the Implied-Return Calculator keeps typed tickers on Scoring's row + 1, while every typed input (Rules 9-14, Implied-Return scenarios) stays on its row. Alan's `_REVIEW` copy had Scoring sorted by Tier 1 average (blank rows hidden at the top): 48 of 49 Entry Checklist rows then showed another ticker beside inputs typed for VEEV, SLB, GE and the rest, and the Dashboard's first rows read blank -- no error anywhere. `landry audit` now has `scoring_row_order` (the typed Implied-Return tickers must sit one row below their Scoring row; it fails on that copy) and Scoring A1 says do-not-sort. The Dashboard table's filter buttons are fine for FILTERING only (added 10/8; its footer is a SUBTOTAL(103) visible count), never for sorting its formula mirror. That copy was NOT promoted: only its mechanical format edits were ported (gridlines off on Current Positions / Entry Checklist / Scratchpad, Entry Checklist frozen at C3, Returns (Calc) at B3, Dashboard filter buttons, Performance Tracking font sizes, 24 column widths). Excel re-serializes alignment on every cell (`general`/`bottom` -> unset: thousands of false differences) and openpyxl's `freeze_panes` reports the SCROLL position, not the split -- compare `sheet_view.pane.xSplit/ySplit` -- so diff a review copy against the exact commit it was copied from, ignoring alignment. `audit`'s `page_setup` check flags a deliberate gridlines change until it is committed.

## Environment and scratch copies (moved verbatim)

- **If `python3` refuses to run with "You have not agreed to the Xcode license agreements"**: the system Python (`/usr/bin/python3`) is gated behind an unaccepted Xcode CLT license (`sudo xcodebuild -license`, which needs an interactive terminal + password — not something to ask the user to stop and do mid-task). Found 2026-09-29, likely triggered by an OS/Xcode update. Fixed without needing the user: Homebrew's own Python (`/opt/homebrew/bin/python3.12`, if present) isn't gated by the same license, but its site-packages are externally-managed (PEP 668) and refuse a global `pip install`. Made a dedicated venv instead — `/opt/homebrew/bin/python3.12 -m venv /Users/Alan/.venvs/stock_picker`, then `/Users/Alan/.venvs/stock_picker/bin/python -m pip install -r requirements.txt` — and used `/Users/Alan/.venvs/stock_picker/bin/python` in place of `python3` for the rest of that session. `landry doctor` confirms an environment is fully ready (also checks `soffice`, since LibreOffice is a separate system binary this doesn't touch). If the venv already exists next time, just use it directly.

- Any file with "copy" in the name (e.g. `..._copy.xlsx`, `TAB UPDATING..._copy.docx`) is the user's own scratch/viewing copy, made by Alan himself while live-editing/discussing a tracked file — never read it as a source of truth or write to it, *unless* the user explicitly names it and asks you to look at it (that overrides the default, since there's no risk of confusing it with a canonical file at that point). **These can be deleted outright, not just left alone or archived** (confirmed 2026-10-01: Alan doesn't need them kept — he saves anything he actually wants to preserve to a Dropbox folder with no connection to the repo). Found and removed 10 of these on that date (most were untracked/gitignored already, one — `Chase_positions_9-4-2026_copy..xlsx` — predated the 8/25 gitignore fix and was still tracked). **Exception: `LANDRY_SYSTEM_WORKBOOK_25_JOURNAL_COPY.xlsx` is NOT one of these** despite the name — it's a Claude-built standing artifact (see the Journal-sort-order bullet below) with a real, ongoing purpose and its own regeneration process, not an ephemeral copy Alan made for himself. Don't delete it on the strength of this rule; it needed its own explicit carve-out even from Alan.
