# Journal, Drawdown Log, database migration, JOURNAL_COPY

- **Journal and Portfolio Drawdown Log entries are written ONLY through `python -m landry journal|drawdown|db` — never by editing those two tabs with openpyxl (switched on 2026-10-02).** `python -m landry journal add --label LABEL [--date YYYY-MM-DD] --notes-file - <<'EOF' … EOF` appends an entry (a quoted heredoc means quotes and paragraphs need no escaping; the date defaults to today); `journal edit --row N …` changes one by the sheet row it is cited by (e.g. to mark it superseded in place); `drawdown add --date YYYY-MM-DD --value N [--notes …]` / `drawdown edit --date …` log or correct a portfolio value. Each command guards, writes the database, regenerates the tab and runs the recalc itself — no separate `xlsx_recalc` for that write — but you still run `python -m landry audit` before committing. A write refuses, leaving everything untouched, if Excel has the workbook open or if `landry.db` and the tab disagree (e.g. Alan hand-edited a cell): `python -m landry db status` shows which, then `db pull` (the workbook is right) or `db regenerate` (the database is right). A fresh checkout has no `landry.db` (it is gitignored and local); the first write builds it from the workbook. These tabs are *generated*, so a hand edit is reset by the next write — their formatting and row heights too (Alan can turn wrapping off to scan rows; the next write restores it) and the Drawdown Log's formulas, whose Part 7 band thresholds now live in `landry/generate.py`. The first write after switch-on re-fits the existing Journal rows (column-B wrap on, heights re-fit); that is expected. Design, rationale and validation: `LANDRY_DATABASE_DESIGN.md`.

- Journal is a **decision log**, not living documentation — entries reflect what was true and decided *at the time they were written*. Don't retroactively edit an old entry to match current reality (that erases the record); add a new entry that references the old one instead. A stale fact in an old entry (e.g. a row number that's since shifted) is expected aging, not a bug — unless the entry's *substance* (a decision, a rationale) has actually been superseded, in which case mark it superseded in place rather than silently leaving it to look current. Marking an entry superseded in place is `python -m landry journal edit --row N --notes "…"` (see the Mandatory bullet on how entries are written).

- When a Journal event label gets reused for a revised plan (e.g. replacing a 12-tranche schedule with an 8-tranche one that reuses `DCA-CATCHUP-1..8`), relabel the *old* entries first (a `-V1` suffix or similar) before writing new ones with the clean label — Process Checklist's due-date lookup keys off Journal's ticker/label column by exact match, and two rows with the same label will silently resolve to whichever one comes first.

- **Journal's live-workbook row order must stay write-order (oldest write first), never re-sorted by date.** Because future-dated recurring-event placeholders (DCA-CATCHUP-N, QTR-REVIEW-N, etc.) are written in blocks with dates far ahead of when they were logged, a date-ascending sort pushes old superseded (`-V1`) placeholders to the bottom — which breaks the "read the last ~15-20 rows for current state" bootstrap at the top of this file, since the tail would show stale future placeholders instead of the actual most-recent decisions. Alan wanted date-sorted reading on 2026-09-13; the fix was a separate standalone file, `LANDRY_SYSTEM_WORKBOOK_25_JOURNAL_COPY.xlsx` (Journal only, sorted by date, Alan's preferred print layout baked in) — regenerate it from the live Journal tab if it goes stale, don't hand-edit it, and don't let the live workbook's own Journal tab get re-sorted again. (Now guaranteed by construction: the database orders entries by id, i.e. write order. The JOURNAL_COPY file is still regenerated separately.)

- **Regenerating `LANDRY_SYSTEM_WORKBOOK_25_JOURNAL_COPY.xlsx`** (last done 2026-10-04, 78 → 83 entries; there is no command for it yet, so the steps matter). (1) Read the live Journal's entries (date, label, notes) and stable-sort by date — same-date entries keep write order. (2) Load the EXISTING copy as the template: it carries Alan's print layout (83% scale, fit to one page wide, narrow margins, columns 12/28/120, Arial Narrow 10, title/header in rows 1-4, data from row 5, headers `Date | Event | Notes`); replace rows 5+ and copy row 5's cell styles onto the new rows. (3) `ws.delete_rows` leaves the OLD rows' stored heights attached to the old row numbers — delete the leftover `row_dimensions` explicitly (42 stale heights were silently riding along on the first attempt). (4) Store NO row heights: Excel and LibreOffice auto-fit rows that have none. Alan's old copy held Excel's own autofit heights, all multiples of 14pt, and rounding LibreOffice's fitted height up to the next 14 reproduced 37 of 39 of them, with the other two a line off in either direction, so pinned estimates risk clipping where autofit cannot. (5) NEVER run it through `xlsx_recalc` — the LibreOffice resave wipes the 83% scale; LibreOffice is only for measuring/rendering a scratch copy. (6) Verify entry count, date order, verbatim notes against the live tab, and that scale/margins/widths survived. (7) **Entries too tall for one Excel row are split.** Excel's row ceiling is 409.5pt: 32 wrapped lines at a 12.75pt pitch but only 29 at the 14pt pitch Alan's Excel produced, so cap a row at 28 lines. At column width 120, three entries exceed that (ABT,SLB,CCI,SCORING-EXPORT-BUGS ≈ 44 wrapped lines, DCA-CATCHUP-1-PREP 33, NFLX 31) and would be clipped on screen and in print; split such an entry at blank-line paragraph boundaries into the fewest, most even chunks of ≤ 28 lines, same date, the later chunks labelled `<label> (cont.)` in the Event column, and say so in A3. Verify by merging the `(cont.)` rows back and comparing with the live text. **An earlier version of this bullet said nothing clips (the longest entry "fits in 27 lines") — that was wrong:** it rested on a LibreOffice measurement taken while stale row heights were still attached, which reported 84pt for a 5,798-character entry. Count wrapped lines with the real Arial Narrow metrics (Pillow + `/System/Library/Fonts/Supplemental/Arial Narrow.ttf` at 13.33px, wrap width 841px for column width 120) or let LibreOffice fit a scratch file that has NO stored heights; the two agree to within a line (44 vs 43, 33 vs 33, 31 vs 30). The file is gitignored (`*copy*.xlsx`), so regenerating it never needs a commit.

- **Database migration — Phase C is LIVE for the Journal and the Portfolio Drawdown Log (switched on 2026-10-02); every other tab is still edited directly with openpyxl + recalc.** Those two tabs are *generated* from `landry.db` (`landry/models.py`, `generate.py`, `ledger.py`) and entries are written only through `python -m landry journal|drawdown|db` — the rules are in the Mandatory section. Until Turso, the **committed workbook is the persisted source of truth** and `landry.db` (gitignored, local, rebuildable with `db pull`) is a write-through cache that a drift guard keeps honest; when Turso replaces the local file this inverts. The Drawdown Log generator writes the tab's own formulas (the DB stores only date/value/notes), so the Part 7 band thresholds, labels, cash floors and new-position rules live in `generate.py` — change them there, not in the sheet; `drawdown.py`'s regime logic is a different thing and is not the source. `landry export --drawdown` is retired (it wrote static regime values over the tab's formulas). **Decisions (2026-10-01):** C-only, not a separate Phase B — Phase B's benefit (reading from the DB) wouldn't have prevented any bug this project has hit, since every one came from hand-editing the xlsx; roll Phase C out incrementally by tab — Journal and Drawdown Log first, the formula-heavy tabs (Scoring's computed columns, Correlation Matrix, Returns, Action Items, Dashboard) once the pattern has proven itself; local SQLite first, Turso once the logic is validated (the original Turso motivation, Alan/Taylor local-DB divergence, is dormant while Taylor is suspended from contributions; Alan and Taylor agree SQLite→Turso is straightforward later). Full history, validation numbers and the switch-on checklist: `LANDRY_DATABASE_DESIGN.md` ("Phase C, step 1", "2", "3").
