# Scoring tab, `landry export`, reader bounds, score store, draft gaps

<!-- Moved verbatim from CLAUDE.md on 2026-10-09 (token diet). CLAUDE.md names the files to read before touching each area. -->

- **`landry/export.py`'s ticker→row lookups (Market Data fill, `--scores` write) used to hardcode `range(3, 28)`** — a stale "tickers only go to row 27" assumption from when the workbook was smaller. Fixed 2026-09-13 to scan the sheet's real extent (`ws.max_row`) after DPZ/PG/GE (rows 32/34/43) were silently skipped by `export --scores` with no error at all — same root cause as the recurring reader-bound class below, just as a *writer* bound this time, and in `export.py` rather than `xlsx_io.py`. If a future export silently does nothing for a ticker, check this file for another instance of the same pattern before assuming the approval didn't take.

- **`export --scores` re-stamps *every* approved ticker's Date Scored with today's date, not just ones actually changed in this run** — `cli.py` passes a single `dt.date.today()` for the whole batch, and `export_workbook` applies it to every row it touches. Confirmed 2026-09-13: exporting DPZ/PG/GE's new scores also silently bumped V's and ET's Date Scored to today even though neither was re-approved. Currently handled by manually reverting the untouched tickers' Date Scored after every `--scores` export — check `git diff` on the Scoring tab's column C after running it, not just the tickers you meant to touch. A real fix would derive each ticker's stamp from its indicators' own `approved_at` rather than one global "today," but `approved_scores()` currently discards `approved_at` when converting to `IndicatorScore` — not done, logged here instead. **It recurred and went unreverted on 2026-09-30** (commit `2c658fa`, the ADBE/PLD/VRTX Tier 1 reconfirmation): 21 tickers' Date Scored became 9/30, 18 of them with no re-score at all (real last approval 9/13). Found 10/5 while checking the "30+ days stale" step and reverted that day; the method is to compare every Scoring row's Date Scored with the latest `approved_at` in `landry_scores.json` (and with the previous commit's column C) — a ticker whose date is newer than its newest approval was re-stamped. A re-stamp makes an old, unverified score look fresh to exactly the staleness test the DCA prep steps rely on, so check column C after ANY export that writes scores.

- **`export --scores`'s new-ticker placement used to treat the Scoring tab's SUBTOTAL ticker-count footer as a real ticker.** Its column-A value is a bare number under `data_only=True`, but the *formula text itself* — still a string — under `data_only=False`, which `export_workbook` must use (loading `data_only=True` and then saving would wipe every other formula in the workbook). A plain non-empty or `isinstance(str)` check lets the footer through either way, corrupting where new rows land. Found 2026-09-13 when adding ABT/SLB: ABT landed at row 63 past the footer with no Company name, and SLB vanished entirely from a second bug in the same block (the free-row counter only ever allowed exactly one new ticker per export call). Both fixed in `export.py` — exclude non-string *and* formula-text (`startswith("=")`) values from the row scan, and let the free-row counter increment per new ticker rather than capping at one. If you're ever again chasing "a new ticker landed somewhere weird" or "one of several new tickers didn't show up at all," this is almost certainly it.

- **To add ONE newly scored ticker to the Scoring tab, call `export_workbook` directly for that ticker rather than running `landry export --scores` (found 2026-10-02 adding VEEV).** The CLI writes *every* ticker in `landry_scores.json` (re-stamping each Date Scored and rewriting rows from the store, which silently overwrites any hand edit made in the workbook since), fills Market Data from `landry_snapshot.json` whenever that file exists (it was the 9/29 snapshot and would have regressed live prices), and writes a `_filled_<date>.xlsx` *copy* unless `--out` names the live file. The targeted form is `export_workbook(P, out_path=P, approved_scores={"TICKER": store.approved_scores("TICKER")}, scored_date=today)` — it touches only that ticker's row (ticker, date, 12 scores + confidences). Then fill Company/Sector/Industry by hand, copy the previous row's cell styles (the Date Scored number format differs on the blank pre-built rows), and recalc. Scoring has pre-built formula rows 51-60 (footer SUBTOTAL at row 62), so nothing needs inserting there until they run out. The Dashboard mirror is a different story: VEEV took Dashboard row 50 (the former blank gap above the note), `DashboardTable` is now A1:J50, its colour rules (which had stopped at row 46, leaving KGS/NFLX/ABT/SLB uncoloured) now run to row 50, and Schema Reference C26 says A1:J50. **The next new ticker needs a real row insertion on Dashboard** (shift the note and the SUBTOTAL footer down and re-derive the footer's range) — that is row surgery, see the openpyxl row-surgery bullet above, and the result should be opened in real Excel once.

- **`read_scoring_tab` (xlsx_io.py) had no `max_row` bound at all on `main` and only checked bare truthiness of column A** — meaning it silently read the Scoring tab's SUBTOTAL footer as a real extra "ticker" (literally named after whatever the current visible count happened to be) on every call, including through `export.import_scores` which calls it internally. This is the third occurrence of the unbounded-reader-treats-a-footer-as-data class in this codebase (previously `read_market_data`/`read_performance_tracking`, then `read_entry_checklist`/`read_monitor_notes`) — a `max_row=60` fix for this exact function had already been made once, but only on the abandoned `db-migration-prep` branch, and was never ported to `main`. Fixed for real 2026-09-13 with a content-based guard (`isinstance(r[0], str)`) rather than a hardcoded row bound, so it can't go stale as the tab grows the way a magic-number bound already has three times over.

- **`read_price_history` (xlsx_io.py, `db-migration-prep` branch) had the same unbounded-reader-treats-a-footer-as-data flaw — the fourth occurrence of this class — found 2026-10-01 resuming the DB re-validation pass.** It choked on Price History's "NN Weeks" count footer (`=COUNT(A3:A163)` in the live workbook). Fixed with a content-based guard matching `read_scoring_tab`'s pattern: real rows always have a `datetime` in col A, the footer has a bare int. Separately, and more importantly, the SAME re-validation pass found a real data bug, not just a reader bug: Price History had two rows both dated 9/4/26 (158 and 163), with row 163's values from AVGO onward looking column-shifted relative to row 158 rather than a second real week — Alan's read: a likely artifact of the original hand-entered 3-year price migration, exact mechanism not reconstructable. This wasn't inert — `Returns (Calc)` row 162 actively computed off Price History rows 162→163, feeding Correlation Matrix and the Rule 38 check. Fixed expediently per Alan ("most expedient correction... current updating process should eliminate this kind of error moving forward"): cleared row 163's cells entirely rather than reconstructing them. Zero formula rewrites needed — `Returns (Calc)`'s formulas already guard every Price History reference with `ISNUMBER`, so a blank row computes as blank, and the week-count footer self-corrected (161→160) since it's a live `COUNT()`, not a hardcoded number. Full detail: Journal row 72.

- **`landry draft` silently dropped the FCF yield, FCF margin and valuation drafts whenever a company's yfinance cash-flow statement has no "Capital Expenditure" row** — found 2026-10-02 on VEEV, whose statement carries a reported "Free Cash Flow" row (equal to CFO in every year) but no capex line. `fcf_series()` needs both CFO and capex, returned `[]`, and nothing said so: the CLI also never printed `FundamentalMetrics.warnings`. Fixed in `landry/fundamentals.py` — `capex_from_reported_fcf()` derives capex as CFO minus reported FCF when the capex row is missing (zero for VEEV, so its FCF is slightly overstated, and a warning says so), `compute_metrics` warns when there is no FCF series at all, and `_cmd_draft` now prints every warning as a `note:` line. Of the 46 tickers in the score store only PLD (a REIT) shared the gap. If a draft is ever missing `fcf_yield_trend`/`fcf_margin_trend`, look for a `note:` line first, then at the yfinance statement rows. A "quant-only Tier 1" average computed from fewer indicators than the usual three is not comparable to one computed from all three — count the indicators before comparing.

- **`landry_scores.json`** (via `landry.approvals.ScoreStore`) — the Part 12 approval audit trail. Any ticker score finalized conversationally (not through `landry draft`'s CLI path) needs to be logged here too (`propose` + `approve`) or it's silently missing from the audit trail despite being live in the Scoring tab.

- **`landry audit`'s `scoring_verification` check** (added 2026-09-13) — flags any Scoring-tab ticker with a real Tier 1 Wtd Avg but no genuine `landry_scores.json` backing (`no_audit_trail`, one consolidated finding — expect a large baseline right now, most of the workbook predates this discipline, see below), and any ticker whose approved indicators show 3+ `source="manual"` entries sharing one identical timestamp **and** an empty or duplicated rationale (`bulk_import` — the fingerprint of `export.import_scores` copying whatever was already in the workbook rather than real per-indicator review). The rationale condition was added 2026-10-02: VEEV's three researched judgments were approved in one scripted call, landed in the same second, and tripped the timestamp-only version on a genuine review — so give every manual approval its own real rationale text. This is exactly the tooling gap that let V sit on an unverified score from 8/11/26 through a live purchase on 9/8/26 — see the Journal for 2026-09-13.

- **Most of the Scoring tab predates `landry_scores.json` and `landry draft` entirely.** landry_scores.json wasn't tracked in git until 2026-08-18; every ticker scored before that (roughly the whole original Darryl-list batch, 8/10-8/13/26 — LIN, ET, DPZ, PG, YUM, V, NFLX, GE, CMG, ETSY, and by extension most of the workbook's other early tickers) came from a pre-tooling conversational chat analysis (`Darryl_List_Analysis_v1.docx`), not this codebase's reproducible, evidence-cited pipeline. Rechecked so far: LIN, ET, DPZ, YUM, and V (a live $18K+ position) all showed real deterioration on fresh data; GE improved; NFLX held steady. `landry audit`'s `scoring_verification` check now makes the remaining unverified backlog visible (25 tickers as of 2026-09-13, down from ~38 at the check's creation as the held-position queue and new Darryl-list screening work through it) — that list is expected to shrink over time as tickers get rechecked, not something to clear in one sitting. Don't treat an old score as reliable for a new decision just because it's sitting in the Scoring tab with a plausible-looking number.
