## Mandatory, every time

- **Run `python -m landry.xlsx_recalc LANDRY_SYSTEM_WORKBOOK_25.xlsx` after every single save**, even a pure styling/no-formula change. openpyxl wipes cached formula values workbook-wide on save; skipping this makes the workbook look broken (blank cells) when it isn't.
- **Run `python -m landry audit` before committing anything that touches the workbook.** Checks Table ranges vs. live data, hardcoded reader bounds in `landry/`, cross-tab formula references, page setup/footer survival, and Schema Reference accuracy. A clean run doesn't replace judgment on whatever you just changed — it's a floor, not a substitute for actually checking your work.
- **Never commit without the user explicitly saying so in that instance.** Approval doesn't carry over from a prior commit.
- **Never hand-roll a portfolio-value or position-aggregation calculation — use `landry.xlsx_io.total_portfolio_value(read_positions(wb))`.** Found 2026-09-29: an ad hoc inline script from 2026-09-13 (computed by summing Current Positions market values without excluding zero-quantity legacy rows) came out to exactly double the real figure ($1.55M vs. the true ~$777K) and was quoted to Alan as fact for several days, including as the basis for an ETF-sleeve percentage (21.7%, actually ~44%) in a still-open design conversation. The tested library function gives the right answer immediately — there was never a reason to reinvent this.

## File conventions

- New `.xlsx` deliverables: Arial Narrow, 10pt. New `.docx` deliverables: Calibri, 11pt. Not retroactive — match whatever an existing file already uses.
- A full-teardown-rebuild of a worksheet (`wb.remove()` + `wb.create_sheet()`, the standard pattern for any structural change) starts with **zero** page setup. Explicitly capture and restore `page_setup` (paperSize/scale/orientation), `page_margins`, and `oddFooter`/`oddHeader` (text+font+size per section) from the last git commit or another already-correct tab — not just font/fill/column-widths. This has been missed and had to be re-fixed more than once; neither recalc nor a value diff will ever catch it.
- Separately, `python -m landry.xlsx_recalc` itself round-trips the file through headless LibreOffice (`soffice`), and that resave normalizes page setup — an explicit `scale` (e.g. 100) tends to come back unset, and `paperSize` can shift to whatever LibreOffice's own default resolves to on this machine (observed: unset → 1/Letter). Found 2026-09-13 when a deliberately-set custom scale on Journal (83%, tight margins, for a print-friendly layout) got silently wiped by the very next mandatory recalc. Since recalc is required after *every* save, a custom non-100% scale on any sheet in the main workbook cannot currently survive — there's no way to both keep cached formula values correct (needs recalc) and keep a custom scale (recalc erases it) with the current tooling. If a sheet genuinely needs a non-default print layout, put it in a standalone extract file instead (see `LANDRY_SYSTEM_WORKBOOK_25_JOURNAL_COPY.xlsx` below) where there's no formula/recalc round-trip to fight. Fixing this properly would mean having `xlsx_recalc` snapshot and reapply page setup via the same LibreOffice pass (a UNO macro), not an openpyxl pass afterward (which would just wipe cached values again) — not done, not urgent while paperSize keeps landing on the correct value (Letter) anyway.
- When a rebuild shifts a tab's column or row positions, grep every *other* tab for `'<TabName>'!` references before calling it done — a within-sheet check never surfaces a stale cross-tab reference. `landry audit` catches most of this automatically now, but it doesn't catch every case (e.g. a formula that still resolves to a *valid but wrong* cell after a column shift — see the Recommended Action bug, or the DCA-CATCHUP-1..8 label collision, both found by hand).
- **Row surgery with openpyxl (`insert_rows` and friends) silently leaves behind everything that isn't cell text — merged ranges, row heights, and every formula whose references aren't inside a Table's structured refs — and Excel is the only thing that notices.** Found 2026-10-02, when Excel answered the workbook with "We found a problem with some content … recover?": the 9/30 GE/NFLX insertion on Current Positions left the note's merge (A50:M50) behind, now *inside* the grown `CurrentPositionsTable` (Excel cannot represent a merged cell inside a Table), and the note itself in an un-merged 11-wide wrapped cell that LibreOffice auto-fit to 941pt (Excel's maximum is 409.5pt). The same surgery wiped the COMBINED PORTFOLIO TOTAL row (a write into a merged range is silently dropped) and left the Excluding-Cash and Cash / Cash Equivalents formulas pointing at their old rows (cash read $396K instead of $469K, the cash % blank) — unnoticed for three days because nothing outside the block reads it. Repaired 10/2 from the pre-surgery workbook (git `f7bbe36`), the total verified against `total_portfolio_value` to the cent. Guards now: `landry audit` has `merges_inside_tables` and `row_height_ceiling`, and `xlsx_recalc` caps any row above 409.5pt on every save and returns `clamped_rows` — if that is ever non-empty the note needs a better layout (merge it across the table width), the cap only keeps the file openable. After ANY row insertion: unmerge/re-merge, re-set heights, re-derive every formula below the insertion *by ticker, not row arithmetic*, write merged-range cells only after unmerging, and open the result in real Excel once — LibreOffice and openpyxl accept files Excel rejects. **Since 2026-10-07 a position is added to Current Positions with `landry.cp_tab.insert_position(wb, account, ticker, description, asset_class, quantity, cost_basis, price)`, never `insert_rows`:** it moves everything below the block down one row the way Excel would (cells with styles, row heights, merges, the Table range), rewrites every same-sheet reference by `shift_formula` (a block-sum range ending on the row above grows to take the new row), copies the block's last row's formulas, and refuses (`CurrentPositionsError`) rather than guess when the sheet's structure differs; `fix_excluding_cash` re-derives the "Excluding Cash" line by ticker. `tests/test_landry_cp_tab.py` pins it, including the invariant that adding a zero-share row to the live workbook changes no number. It still needs the open-in-Excel check. First used for VEEV (row 24, Journal row 104); the same pass found the JT ULTRA "Excluding Cash" line had subtracted Visa's cost instead of FZFXX's since the 9/8 insertion (7.2% -> 6.3%). Known and deliberately left alone (Alan, 10/2): FZDXX/FZFXX cost basis wasn't reduced by the $44,541.75 spent on GE/NFLX, so Combined unrealized G/L reads ~$15K instead of ~$60K — an interim estimate that corrects itself on the next real Fidelity export; don't hand-fix it.
- **LibreOffice's recalc will NOT catch a circular reference that Excel reports -- and Excel is the only thing that does.** Found 2026-10-05, before it reached Excel, on Performance Tracking: `Shares` used `SUMIFS($T:$T,$A:$A,…,$I:$I,…)` with whole-column ranges, column I also holds the summary block's Excess formulas, and those depend on Shares -- a range-level cycle (`I47 -> G47 -> D47 -> V10 -> U10 -> I47`). Excel treats a formula as depending on EVERY cell of a range it reads, whether or not SUMIFS needs that cell, so it would have shown a circular-reference warning and zeros; LibreOffice evaluates SUMIFS lazily, calculated correct numbers and reported 0 errors. So: never read whole columns from a formula on a tab that also holds formulas below its table; bound ranges to the table's rows. `landry.perf_tab.find_cycles(wb)` does the range-level search for that tab (the audit's `performance_tracking_ties:cycles` runs it every time); if another tab gets formulas that read whole columns, run the same kind of check -- a clean recalc proves nothing about this.
