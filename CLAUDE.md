## Mandatory, every time

- **Run `python -m landry.xlsx_recalc LANDRY_SYSTEM_WORKBOOK_25.xlsx` after every single save**, even a pure styling/no-formula change. openpyxl wipes cached formula values workbook-wide on save; skipping this makes the workbook look broken (blank cells) when it isn't.
- **Run `python -m landry audit` before committing anything that touches the workbook.** Checks Table ranges vs. live data, hardcoded reader bounds in `landry/`, cross-tab formula references, page setup/footer survival, and Schema Reference accuracy. A clean run doesn't replace judgment on whatever you just changed — it's a floor, not a substitute for actually checking your work.
- **Never commit without the user explicitly saying so in that instance.** Approval doesn't carry over from a prior commit.
- **Never hand-roll a portfolio-value or position-aggregation calculation — use `landry.xlsx_io.total_portfolio_value(read_positions(wb))`.** Found 2026-09-29: an ad hoc inline script from 2026-09-13 (computed by summing Current Positions market values without excluding zero-quantity legacy rows) came out to exactly double the real figure ($1.55M vs. the true ~$777K) and was quoted to Alan as fact for several days, including as the basis for an ETF-sleeve percentage (21.7%, actually ~44%) in a still-open design conversation. The tested library function gives the right answer immediately — there was never a reason to reinvent this.
- **Current Positions' own Price column (col F) cannot be refreshed by this tooling — it falls back to a stale hardcoded number whenever Python/LibreOffice touches the file.** The formula chain is Current Positions!F → `INDEX/MATCH` into Monitor & Recheck Triggers!H → a STOCKHISTORY array formula, and STOCKHISTORY is a Microsoft-cloud data type that only resolves inside real Excel with a live connection — `xlsx_recalc`'s LibreOffice pass cannot touch it, so col H (and therefore Current Positions' displayed price) just keeps showing whatever was last live-refreshed the last time Alan had the file open in actual Excel. **Market Data (refreshed via `landry refresh --refresh-data` + `landry export`, both yfinance-backed) is the reliable source for a current price** — use it directly (ticker → Market Data!C) rather than trusting Current Positions' Price/Market Value columns for anything computed outside Excel. Found 2026-09-29 doing a post-travel portfolio revaluation: NVDA showed $230.36 in Current Positions against a genuinely live $227.21 in Market Data, a stale/fresh mismatch that would have gone unnoticed without cross-checking.
- **If `python3` refuses to run with "You have not agreed to the Xcode license agreements"**: the system Python (`/usr/bin/python3`) is gated behind an unaccepted Xcode CLT license (`sudo xcodebuild -license`, which needs an interactive terminal + password — not something to ask the user to stop and do mid-task). Found 2026-09-29, likely triggered by an OS/Xcode update. Fixed without needing the user: Homebrew's own Python (`/opt/homebrew/bin/python3.12`, if present) isn't gated by the same license, but its site-packages are externally-managed (PEP 668) and refuse a global `pip install`. Made a dedicated venv instead — `/opt/homebrew/bin/python3.12 -m venv /Users/Alan/.venvs/stock_picker`, then `/Users/Alan/.venvs/stock_picker/bin/python -m pip install -r requirements.txt` — and used `/Users/Alan/.venvs/stock_picker/bin/python` in place of `python3` for the rest of that session. `landry doctor` confirms an environment is fully ready (also checks `soffice`, since LibreOffice is a separate system binary this doesn't touch). If the venv already exists next time, just use it directly.

## File conventions

- New `.xlsx` deliverables: Arial Narrow, 10pt. New `.docx` deliverables: Calibri, 11pt. Not retroactive — match whatever an existing file already uses.
- A full-teardown-rebuild of a worksheet (`wb.remove()` + `wb.create_sheet()`, the standard pattern for any structural change) starts with **zero** page setup. Explicitly capture and restore `page_setup` (paperSize/scale/orientation), `page_margins`, and `oddFooter`/`oddHeader` (text+font+size per section) from the last git commit or another already-correct tab — not just font/fill/column-widths. This has been missed and had to be re-fixed more than once; neither recalc nor a value diff will ever catch it.
- Separately, `python -m landry.xlsx_recalc` itself round-trips the file through headless LibreOffice (`soffice`), and that resave normalizes page setup — an explicit `scale` (e.g. 100) tends to come back unset, and `paperSize` can shift to whatever LibreOffice's own default resolves to on this machine (observed: unset → 1/Letter). Found 2026-09-13 when a deliberately-set custom scale on Journal (83%, tight margins, for a print-friendly layout) got silently wiped by the very next mandatory recalc. Since recalc is required after *every* save, a custom non-100% scale on any sheet in the main workbook cannot currently survive — there's no way to both keep cached formula values correct (needs recalc) and keep a custom scale (recalc erases it) with the current tooling. If a sheet genuinely needs a non-default print layout, put it in a standalone extract file instead (see `LANDRY_SYSTEM_WORKBOOK_25_JOURNAL_COPY.xlsx` below) where there's no formula/recalc round-trip to fight. Fixing this properly would mean having `xlsx_recalc` snapshot and reapply page setup via the same LibreOffice pass (a UNO macro), not an openpyxl pass afterward (which would just wipe cached values again) — not done, not urgent while paperSize keeps landing on the correct value (Letter) anyway.
- When a rebuild shifts a tab's column or row positions, grep every *other* tab for `'<TabName>'!` references before calling it done — a within-sheet check never surfaces a stale cross-tab reference. `landry audit` catches most of this automatically now, but it doesn't catch every case (e.g. a formula that still resolves to a *valid but wrong* cell after a column shift — see the Recommended Action bug, or the DCA-CATCHUP-1..8 label collision, both found by hand).
- `ws.tables.items()` in this openpyxl version yields `(name, ref-string)`, not `(name, Table object)` — use `ws.tables[name]` (bracket access) to get the real Table object with `.ref`, `.tableColumns`, etc.
- **`landry/export.py`'s ticker→row lookups (Market Data fill, `--scores` write) used to hardcode `range(3, 28)`** — a stale "tickers only go to row 27" assumption from when the workbook was smaller. Fixed 2026-09-13 to scan the sheet's real extent (`ws.max_row`) after DPZ/PG/GE (rows 32/34/43) were silently skipped by `export --scores` with no error at all — same root cause as the recurring reader-bound class below, just as a *writer* bound this time, and in `export.py` rather than `xlsx_io.py`. If a future export silently does nothing for a ticker, check this file for another instance of the same pattern before assuming the approval didn't take.
- **`export --scores` re-stamps *every* approved ticker's Date Scored with today's date, not just ones actually changed in this run** — `cli.py` passes a single `dt.date.today()` for the whole batch, and `export_workbook` applies it to every row it touches. Confirmed 2026-09-13: exporting DPZ/PG/GE's new scores also silently bumped V's and ET's Date Scored to today even though neither was re-approved. Currently handled by manually reverting the untouched tickers' Date Scored after every `--scores` export — check `git diff` on the Scoring tab's column C after running it, not just the tickers you meant to touch. A real fix would derive each ticker's stamp from its indicators' own `approved_at` rather than one global "today," but `approved_scores()` currently discards `approved_at` when converting to `IndicatorScore` — not done, logged here instead.
- **`export --scores`'s new-ticker placement used to treat the Scoring tab's SUBTOTAL ticker-count footer as a real ticker.** Its column-A value is a bare number under `data_only=True`, but the *formula text itself* — still a string — under `data_only=False`, which `export_workbook` must use (loading `data_only=True` and then saving would wipe every other formula in the workbook). A plain non-empty or `isinstance(str)` check lets the footer through either way, corrupting where new rows land. Found 2026-09-13 when adding ABT/SLB: ABT landed at row 63 past the footer with no Company name, and SLB vanished entirely from a second bug in the same block (the free-row counter only ever allowed exactly one new ticker per export call). Both fixed in `export.py` — exclude non-string *and* formula-text (`startswith("=")`) values from the row scan, and let the free-row counter increment per new ticker rather than capping at one. If you're ever again chasing "a new ticker landed somewhere weird" or "one of several new tickers didn't show up at all," this is almost certainly it.
- **`ws.cell(row=r, column=c, value=None)` does NOT clear an existing cell.** The constructor only assigns when the value is truthy/not-`None`, so this call is a silent no-op on a cell that already has content — cost real time on 2026-09-13 debugging why a "clear this row" script kept appearing to do nothing. Clear a cell with explicit attribute assignment instead: `cell = ws.cell(row=r, column=c); cell.value = None`.
- **`read_scoring_tab` (xlsx_io.py) had no `max_row` bound at all on `main` and only checked bare truthiness of column A** — meaning it silently read the Scoring tab's SUBTOTAL footer as a real extra "ticker" (literally named after whatever the current visible count happened to be) on every call, including through `export.import_scores` which calls it internally. This is the third occurrence of the unbounded-reader-treats-a-footer-as-data class in this codebase (previously `read_market_data`/`read_performance_tracking`, then `read_entry_checklist`/`read_monitor_notes`) — a `max_row=60` fix for this exact function had already been made once, but only on the abandoned `db-migration-prep` branch, and was never ported to `main`. Fixed for real 2026-09-13 with a content-based guard (`isinstance(r[0], str)`) rather than a hardcoded row bound, so it can't go stale as the tab grows the way a magic-number bound already has three times over.
- **`read_price_history` (xlsx_io.py, `db-migration-prep` branch) had the same unbounded-reader-treats-a-footer-as-data flaw — the fourth occurrence of this class — found 2026-10-01 resuming the DB re-validation pass.** It choked on Price History's "NN Weeks" count footer (`=COUNT(A3:A163)` in the live workbook). Fixed with a content-based guard matching `read_scoring_tab`'s pattern: real rows always have a `datetime` in col A, the footer has a bare int. Separately, and more importantly, the SAME re-validation pass found a real data bug, not just a reader bug: Price History had two rows both dated 9/4/26 (158 and 163), with row 163's values from AVGO onward looking column-shifted relative to row 158 rather than a second real week — Alan's read: a likely artifact of the original hand-entered 3-year price migration, exact mechanism not reconstructable. This wasn't inert — `Returns (Calc)` row 162 actively computed off Price History rows 162→163, feeding Correlation Matrix and the Rule 38 check. Fixed expediently per Alan ("most expedient correction... current updating process should eliminate this kind of error moving forward"): cleared row 163's cells entirely rather than reconstructing them. Zero formula rewrites needed — `Returns (Calc)`'s formulas already guard every Price History reference with `ISNUMBER`, so a blank row computes as blank, and the week-count footer self-corrected (161→160) since it's a live `COUNT()`, not a hardcoded number. Full detail: Journal row 72.
- **A tab that formula-mirrors another (Dashboard mirrors Scoring row-for-row) needs its own row range extended every time the source tab grows a row** — this is a *fourth* variant of the cross-tab-drift problem, distinct from a stale column reference or a truncated range formula, because each mirror row is a single-cell reference (`=IF(Scoring!A48="","",Scoring!A48)`) that `landry audit`'s `check_cross_tab_references` doesn't flag (it checks header validity and range coverage, not "a whole row is simply missing"). Found 2026-09-13: Dashboard's mirror stopped at Scoring row 47, so KGS (added 9/11, row 48) was already invisible on Dashboard before ABT/SLB made it worse. If you add a new ticker row to Scoring, check whether Dashboard's last mirror row still covers it — `landry audit`'s `table_ref` check *will* catch the resulting Table-ref-vs-data mismatch once you extend the mirror rows but forget to extend `DashboardTable`'s own ref, and `schema_ref` will catch Schema Reference's row-range note going stale after that — but nothing catches the missing mirror rows themselves.
- Journal is a **decision log**, not living documentation — entries reflect what was true and decided *at the time they were written*. Don't retroactively edit an old entry to match current reality (that erases the record); add a new entry that references the old one instead. A stale fact in an old entry (e.g. a row number that's since shifted) is expected aging, not a bug — unless the entry's *substance* (a decision, a rationale) has actually been superseded, in which case mark it superseded in place rather than silently leaving it to look current.
- **Scoring's Composite Score gate (col AF) now requires every Tier 1/2/3 indicator individually populated**, not just "the tier's contribution cell happens to be non-blank" — fixed 2026-09-13 tab-wide when GE became the first ticker ever scored with a genuinely partial Tier 2 (3 of 4 quant indicators drafted, Management Quality still pending a human call). The old gate would have silently computed Composite treating the missing indicator as a 0 contribution instead of waiting. Same idea as the Tier 1 Wtd Avg zero-padding fix from the KGS addition — if you're populating Tier 2/3 for a new ticker, do all of a tier's indicators in one pass rather than leaving it partially filled between saves, even though the gate itself is now safe either way.
- When a Journal event label gets reused for a revised plan (e.g. replacing a 12-tranche schedule with an 8-tranche one that reuses `DCA-CATCHUP-1..8`), relabel the *old* entries first (a `-V1` suffix or similar) before writing new ones with the clean label — Process Checklist's due-date lookup keys off Journal's ticker/label column by exact match, and two rows with the same label will silently resolve to whichever one comes first.
- **Journal's live-workbook row order must stay write-order (oldest write first), never re-sorted by date.** Because future-dated recurring-event placeholders (DCA-CATCHUP-N, QTR-REVIEW-N, etc.) are written in blocks with dates far ahead of when they were logged, a date-ascending sort pushes old superseded (`-V1`) placeholders to the bottom — which breaks the "read the last ~15-20 rows for current state" bootstrap at the top of this file, since the tail would show stale future placeholders instead of the actual most-recent decisions. Alan wanted date-sorted reading on 2026-09-13; the fix was a separate standalone file, `LANDRY_SYSTEM_WORKBOOK_25_JOURNAL_COPY.xlsx` (Journal only, sorted by date, Alan's preferred print layout baked in) — regenerate it from the live Journal tab if it goes stale, don't hand-edit it, and don't let the live workbook's own Journal tab get re-sorted again.
