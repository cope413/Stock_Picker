## Mandatory, every time

- **Run `python -m landry.xlsx_recalc LANDRY_SYSTEM_WORKBOOK_25.xlsx` after every single save**, even a pure styling/no-formula change. openpyxl wipes cached formula values workbook-wide on save; skipping this makes the workbook look broken (blank cells) when it isn't.
- **Run `python -m landry audit` before committing anything that touches the workbook.** Checks Table ranges vs. live data, hardcoded reader bounds in `landry/`, cross-tab formula references, page setup/footer survival, and Schema Reference accuracy. A clean run doesn't replace judgment on whatever you just changed — it's a floor, not a substitute for actually checking your work.
- **Never commit without the user explicitly saying so in that instance.** Approval doesn't carry over from a prior commit.
- **Never hand-roll a portfolio-value or position-aggregation calculation — use `landry.xlsx_io.total_portfolio_value(read_positions(wb))`.** Found 2026-09-29: an ad hoc inline script from 2026-09-13 (computed by summing Current Positions market values without excluding zero-quantity legacy rows) came out to exactly double the real figure ($1.55M vs. the true ~$777K) and was quoted to Alan as fact for several days, including as the basis for an ETF-sleeve percentage (21.7%, actually ~44%) in a still-open design conversation. The tested library function gives the right answer immediately — there was never a reason to reinvent this.
- **Current Positions' own Price column (col F) cannot be refreshed by this tooling — it falls back to a stale hardcoded number whenever Python/LibreOffice touches the file.** The formula chain is Current Positions!F → `INDEX/MATCH` into Monitor & Recheck Triggers!H → a STOCKHISTORY array formula, and STOCKHISTORY is a Microsoft-cloud data type that only resolves inside real Excel with a live connection — `xlsx_recalc`'s LibreOffice pass cannot touch it, so col H (and therefore Current Positions' displayed price) just keeps showing whatever was last live-refreshed the last time Alan had the file open in actual Excel. **Market Data (refreshed every Saturday by `python -m landry weekly`, or on demand with `python -m landry market`; yfinance-backed, a snapshot rather than live — check how recent it is) is the reliable source for a current price** — use it directly (ticker → Market Data!C) rather than trusting Current Positions' Price/Market Value columns for anything computed outside Excel. Found 2026-09-29 doing a post-travel portfolio revaluation: NVDA showed $230.36 in Current Positions against a genuinely live $227.21 in Market Data, a stale/fresh mismatch that would have gone unnoticed without cross-checking. **Exception, 2026-10-05: a workbook Alan has just saved from real Excel carries live prices** (the Excel-saved review copy that became the live file had Current Positions!F and Monitor!H populated from STOCKHISTORY, e.g. NVDA 233.95, and a portfolio total ~$6K higher), stored as cached values with Excel's rich-value metadata; the first tool write (any openpyxl save + LibreOffice recalc) strips them and the stale fallback returns, so don't treat them as durable and never run `xlsx_recalc` on such a file just to "refresh" it. **Promoting an Excel-saved review copy to be the live workbook** (Alan: "check the review copy; if it checks out, make it the original"): compare formulas/constants cell by cell (it was 3 header labels, nothing else), list structure/format differences (Excel omits default attributes, writes alignment/page setup differently -- noise -- while freezes, hidden rows, widths, fonts, conditional formats are real), round-trip a scratch copy through openpyxl + `xlsx_recalc` and diff again to see what a tool write would lose, run `landry db status`/`audit`/the tests/`weekly --dry-run` against it, then `mv` it over `LANDRY_SYSTEM_WORKBOOK_25.xlsx` (keep the previous file in the scratchpad) and delete the review copies once Excel has them closed.

- **Journal and Portfolio Drawdown Log entries are written ONLY through `python -m landry journal|drawdown|db` — never by editing those two tabs with openpyxl (switched on 2026-10-02).** `python -m landry journal add --label LABEL [--date YYYY-MM-DD] --notes-file - <<'EOF' … EOF` appends an entry (a quoted heredoc means quotes and paragraphs need no escaping; the date defaults to today); `journal edit --row N …` changes one by the sheet row it is cited by (e.g. to mark it superseded in place); `drawdown add --date YYYY-MM-DD --value N [--notes …]` / `drawdown edit --date …` log or correct a portfolio value. ## File conventions

- New `.xlsx` deliverables: Arial Narrow, 10pt. New `.docx` deliverables: Calibri, 11pt. Not retroactive — match whatever an existing file already uses.
- A full-teardown-rebuild of a worksheet (`wb.remove()` + `wb.create_sheet()`, the standard pattern for any structural change) starts with **zero** page setup. Explicitly capture and restore `page_setup` (paperSize/scale/orientation), `page_margins`, and `oddFooter`/`oddHeader` (text+font+size per section) from the last git commit or another already-correct tab — not just font/fill/column-widths. This has been missed and had to be re-fixed more than once; neither recalc nor a value diff will ever catch it.
- Separately, `python -m landry.xlsx_recalc` itself round-trips the file through headless LibreOffice (`soffice`), and that resave normalizes page setup — an explicit `scale` (e.g. 100) tends to come back unset, and `paperSize` can shift to whatever LibreOffice's own default resolves to on this machine (observed: unset → 1/Letter). Found 2026-09-13 when a deliberately-set custom scale on Journal (83%, tight margins, for a print-friendly layout) got silently wiped by the very next mandatory recalc. Since recalc is required after *every* save, a custom non-100% scale on any sheet in the main workbook cannot currently survive — there's no way to both keep cached formula values correct (needs recalc) and keep a custom scale (recalc erases it) with the current tooling. If a sheet genuinely needs a non-default print layout, put it in a standalone extract file instead (see `LANDRY_SYSTEM_WORKBOOK_25_JOURNAL_COPY.xlsx` below) where there's no formula/recalc round-trip to fight. Fixing this properly would mean having `xlsx_recalc` snapshot and reapply page setup via the same LibreOffice pass (a UNO macro), not an openpyxl pass afterward (which would just wipe cached values again) — not done, not urgent while paperSize keeps landing on the correct value (Letter) anyway.
- When a rebuild shifts a tab's column or row positions, grep every *other* tab for `'<TabName>'!` references before calling it done — a within-sheet check never surfaces a stale cross-tab reference. `landry audit` catches most of this automatically now, but it doesn't catch every case (e.g. a formula that still resolves to a *valid but wrong* cell after a column shift — see the Recommended Action bug, or the DCA-CATCHUP-1..8 label collision, both found by hand).
- **Row surgery with openpyxl (`insert_rows` and friends) silently leaves behind everything that isn't cell text — merged ranges, row heights, and every formula whose references aren't inside a Table's structured refs — and Excel is the only thing that notices.** Found 2026-10-02, when Excel answered the workbook with "We found a problem with some content … recover?": the 9/30 GE/NFLX insertion on Current Positions left the note's merge (A50:M50) behind, now *inside* the grown `CurrentPositionsTable` (Excel cannot represent a merged cell inside a Table), and the note itself in an un-merged 11-wide wrapped cell that LibreOffice auto-fit to 941pt (Excel's maximum is 409.5pt). The same surgery wiped the COMBINED PORTFOLIO TOTAL row (a write into a merged range is silently dropped) and left the Excluding-Cash and Cash / Cash Equivalents formulas pointing at their old rows (cash read $396K instead of $469K, the cash % blank) — unnoticed for three days because nothing outside the block reads it. Repaired 10/2 from the pre-surgery workbook (git `f7bbe36`), the total verified against `total_portfolio_value` to the cent. Guards now: `landry audit` has `merges_inside_tables` and `row_height_ceiling`, and `xlsx_recalc` caps any row above 409.5pt on every save and returns `clamped_rows` — if that is ever non-empty the note needs a better layout (merge it across the table width), the cap only keeps the file openable. After ANY row insertion: unmerge/re-merge, re-set heights, re-derive every formula below the insertion *by ticker, not row arithmetic*, write merged-range cells only after unmerging, and open the result in real Excel once — LibreOffice and openpyxl accept files Excel rejects. Known and deliberately left alone (Alan, 10/2): FZDXX/FZFXX cost basis wasn't reduced by the $44,541.75 spent on GE/NFLX, so Combined unrealized G/L reads ~$15K instead of ~$60K — an interim estimate that corrects itself on the next real Fidelity export; don't hand-fix it.
- `ws.tables.items()` in this openpyxl version yields `(name, ref-string)`, not `(name, Table object)` — use `ws.tables[name]` (bracket access) to get the real Table object with `.ref`, `.tableColumns`, etc.
- **`landry/export.py`'s ticker→row lookups (Market Data fill, `--scores` write) used to hardcode `range(3, 28)`** — a stale "tickers only go to row 27" assumption from when the workbook was smaller. Fixed 2026-09-13 to scan the sheet's real extent (`ws.max_row`) after DPZ/PG/GE (rows 32/34/43) were silently skipped by `export --scores` with no error at all — same root cause as the recurring reader-bound class below, just as a *writer* bound this time, and in `export.py` rather than `xlsx_io.py`. If a future export silently does nothing for a ticker, check this file for another instance of the same pattern before assuming the approval didn't take.
- **`export --scores` re-stamps *every* approved ticker's Date Scored with today's date, not just ones actually changed in this run** — `cli.py` passes a single `dt.date.today()` for the whole batch, and `export_workbook` applies it to every row it touches. Confirmed 2026-09-13: exporting DPZ/PG/GE's new scores also silently bumped V's and ET's Date Scored to today even though neither was re-approved. Currently handled by manually reverting the untouched tickers' Date Scored after every `--scores` export — check `git diff` on the Scoring tab's column C after running it, not just the tickers you meant to touch. A real fix would derive each ticker's stamp from its indicators' own `approved_at` rather than one global "today," but `approved_scores()` currently discards `approved_at` when converting to `IndicatorScore` — not done, logged here instead.
- **`export --scores`'s new-ticker placement used to treat the Scoring tab's SUBTOTAL ticker-count footer as a real ticker.** Its column-A value is a bare number under `data_only=True`, but the *formula text itself* — still a string — under `data_only=False`, which `export_workbook` must use (loading `data_only=True` and then saving would wipe every other formula in the workbook). A plain non-empty or `isinstance(str)` check lets the footer through either way, corrupting where new rows land. Found 2026-09-13 when adding ABT/SLB: ABT landed at row 63 past the footer with no Company name, and SLB vanished entirely from a second bug in the same block (the free-row counter only ever allowed exactly one new ticker per export call). Both fixed in `export.py` — exclude non-string *and* formula-text (`startswith("=")`) values from the row scan, and let the free-row counter increment per new ticker rather than capping at one. If you're ever again chasing "a new ticker landed somewhere weird" or "one of several new tickers didn't show up at all," this is almost certainly it.
- **To add ONE newly scored ticker to the Scoring tab, call `export_workbook` directly for that ticker rather than running `landry export --scores` (found 2026-10-02 adding VEEV).** The CLI writes *every* ticker in `landry_scores.json` (re-stamping each Date Scored and rewriting rows from the store, which silently overwrites any hand edit made in the workbook since), fills Market Data from `landry_snapshot.json` whenever that file exists (it was the 9/29 snapshot and would have regressed live prices), and writes a `_filled_<date>.xlsx` *copy* unless `--out` names the live file. The targeted form is `export_workbook(P, out_path=P, approved_scores={"TICKER": store.approved_scores("TICKER")}, scored_date=today)` — it touches only that ticker's row (ticker, date, 12 scores + confidences). Then fill Company/Sector/Industry by hand, copy the previous row's cell styles (the Date Scored number format differs on the blank pre-built rows), and recalc. Scoring has pre-built formula rows 51-60 (footer SUBTOTAL at row 62), so nothing needs inserting there until they run out. The Dashboard mirror is a different story: VEEV took Dashboard row 50 (the former blank gap above the note), `DashboardTable` is now A1:J50, its colour rules (which had stopped at row 46, leaving KGS/NFLX/ABT/SLB uncoloured) now run to row 50, and Schema Reference C26 says A1:J50. **The next new ticker needs a real row insertion on Dashboard** (shift the note and the SUBTOTAL footer down and re-derive the footer's range) — that is row surgery, see the openpyxl row-surgery bullet above, and the result should be opened in real Excel once.
- **`ws.cell(row=r, column=c, value=None)` does NOT clear an existing cell.** The constructor only assigns when the value is truthy/not-`None`, so this call is a silent no-op on a cell that already has content — cost real time on 2026-09-13 debugging why a "clear this row" script kept appearing to do nothing. - **`read_scoring_tab` (xlsx_io.py) had no `max_row` bound at all on `main` and only checked bare truthiness of column A** — meaning it silently read the Scoring tab's SUBTOTAL footer as a real extra "ticker" (literally named after whatever the current visible count happened to be) on every call, including through `export.import_scores` which calls it internally. This is the third occurrence of the unbounded-reader-treats-a-footer-as-data class in this codebase (previously `read_market_data`/`read_performance_tracking`, then `read_entry_checklist`/`read_monitor_notes`) — a `max_row=60` fix for this exact function had already been made once, but only on the abandoned `db-migration-prep` branch, and was never ported to `main`. Fixed for real 2026-09-13 with a content-based guard (`isinstance(r[0], str)`) rather than a hardcoded row bound, so it can't go stale as the tab grows the way a magic-number bound already has three times over.

## Standing tools (all built 2026-09-08 through 2026-09-11)

- **`python -m landry audit`** (`landry/audit.py`) — structural drift checker for the workbook itself.
- **Process Checklist tab** — one row per required step for every recurring Journal event (tranches, quarterly reviews, fundamental refreshes). `Status` auto-flags `OVERDUE` once the event's Journal date passes with a step unchecked. Whenever Journal's calendar gets a new recurring event (or an existing one's steps change), reseed this tab in the same pass — the seed script is not currently checked into the repo, it's been rebuilt ad hoc each time; consider writing a real one if this keeps recurring.
- **Open Items tab** — numbered, priority-ordered backlog for ad hoc (non-recurring) open questions. Mark items Done with a date and a one-line pointer to the Journal entry with full reasoning; don't delete resolved rows.
- **`landry_scores.json`** (via `landry.approvals.ScoreStore`) — the Part 12 approval audit trail. Any ticker score finalized conversationally (not through `landry draft`'s CLI path) needs to be logged here too (`propose` + `approve`) or it's silently missing from the audit trail despite being live in the Scoring tab.
- **`landry audit`'s `scoring_verification` check** (added 2026-09-13) — flags any Scoring-tab ticker with a real Tier 1 Wtd Avg but no genuine `landry_scores.json` backing (`no_audit_trail`, one consolidated finding — expect a large baseline right now, most of the workbook predates this discipline, see below), and any ticker whose approved indicators show 3+ `source="manual"` entries sharing one identical timestamp **and** an empty or duplicated rationale (`bulk_import` — the fingerprint of `export.import_scores` copying whatever was already in the workbook rather than real per-indicator review).
